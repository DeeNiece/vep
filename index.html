Documentation gap: v2.6 → current

This guide was last fully synced when both cBots sat at v2.6 and the indicator at v2.5. Several development sessions happened between then and now that aren't individually itemized below — VPDC moved v2.6 → v2.20, VEPX moved v2.6 → v1.14 (switching to its own 1.x version track along the way), and the indicator moved v2.5 → v2.10, before the session documented in full below took every file to its current version. The Parameter Reference tables further down this guide reflect every parameter that exists in the current code, regardless of which session added it — so nothing is missing from the reference material, even though the blow-by-blow changelog has this one gap.

What's New — Sep 2026 (Indicator v2.16 → v2.22)

Driven by dashboard refinements, a new MA Cross feature built out across three follow-up fixes, and a new manual-backup confirmation alert for EDGE EXH.

ADDEDv2.16 — Spread added to the dashboard: Combined into the existing POC NODE row (now labeled POC / SPREAD) rather than as its own new row — Symbol.Spread divided by PipSize, matching the pip-conversion pattern used everywhere else in this dashboard. Color stays driven by POC strength alone, unaffected by the spread value.
FIXEDv2.17 — POC / SPREAD precision: Now shows spread to 3 decimal places, was 1.
ADDEDv2.18 — Max Alerts Per Symbol Per Day, new Communications group: 0 means unlimited — the opposite of the cBots' own Max Trades For Symbol Per Day, deliberately: there, 0 was forbidden because it would silently duplicate what Enable Trading already does. Here, Enable Alerts already owns "no alerts at all," so 0 is free to mean its natural, unambiguous "no cap" instead. One shared counter covers every alert type combined (VA TRAP, EDGE EXH, POC BOUNCE, REJECTION, and the separate PDC Cross Alert), self-correcting on a new day like the cBots' own version.
ADDEDv2.19 — MA Cross, new "MA Cross" group: Two configurable moving averages (type, length, color, width, style each independently) plus a "+" marker at every cross, colored by direction — matching VMAX's own confirmation mechanism visually, but purely observational here, since this indicator never places trades. Marker drawing bounded by a configurable lookback, same lesson already learned building the standalone MA Cross indicator this is based on.
FIXEDv2.20 — MA Cross visible on/off flicker: Calculate() runs on every tick, not once per bar close, and the drawing function was doing a full remove-then-redraw of every MA Cross chart object it owns on every single tick — up to hundreds of objects during active price movement, visibly flickering. Fixed with a bar-index guard so the expensive full redraw only actually runs once per genuinely new bar. Toggling Show MA Cross off still clears immediately regardless, rather than waiting for the next bar.
ADDEDv2.21 — MA Cross Marker Size: A real gap — v2.19's own cross marker was hardcoded to a fixed font size with no way to change it, unlike both VMAX's cBot version and the standalone MA Cross indicator, which already had this exact parameter from the start.
ADDEDv2.22 — MA Cross Confirmation Alert, a new manual-backup notification for EDGE EXH: Requested specifically so a real backward MA cross can be seen alongside a genuinely fired EDGE EXH signal, even when the corresponding cBot isn't running or has failed. Deliberately a single-moment backward check only — checks whether a matching-direction MA cross already happened within Backward Cross Lookback (bars), with no ongoing forward wait if nothing's found — not VMAX/VSMA's own full watch-and-wait mechanism, since this indicator places no orders and has no pending state to track or expire. Same feature added to VolumeEdgeProSession at the same time. Draws from the same shared daily alert cap as every other alert type.

What's New — Aug 2026 Part 2 (VPDC v2.31, VEPX v1.24, Indicator v2.15)

Driven by a live FTMO account genuinely exceeding Max Concurrent Trades despite it being set to 1 — traced through several rounds of diagnosis to a real cross-process race — plus a filter-independence bug, a new optional confirmation stage, and closing a real gap in the PDC cross confirmation shared by the indicator and VPDC.

FIXEDBoth cBots (v1.19 / v2.25) — Max Concurrent Trades bypassed across separate processes: Confirmed for real on a live FTMO account: six symbol instances running as six separate cTrader processes each independently read the account's live trade count before any of the others' placement had propagated back, and multiple placed an order in the same moment — with the cap set to 1 on every single instance. The static in-process lock this project already had only ever synchronized threads within one running process; it provided zero protection across separate ones. Replaced with a named, OS-level Mutex scoped to the account number, which genuinely serializes the check-then-place sequence account-wide regardless of how many separate processes are running it.
ADDEDBoth cBots (v1.20 / v2.26) — Post-placement cap re-check: The pre-placement gate can only ever see this instance's own configured cap — it has no way to know if a different, non-cooperating instance (unaware of the lock, or configured with a different cap value) adds its own trade in the narrow gap between this instance's own check and its own placement finishing. Confirmed for real: exactly this happened, two separate instances each correctly respecting their own cap, still pushing the account-wide total over what was intended. This re-counts the account-wide total immediately after placement and cancels this instance's own just-placed order if it's already over cap — scoped to the pending order only, not auto-closing a position if it already filled in that brief window (a loud alert instead).
ADDEDBoth cBots (v1.21 / v2.27) — Standing OVER CAP detector: Catches everything the two checks above can't — a manually-placed Comment-tagged trade, or a fill from a different/duplicate instance neither placement guard ever saw. Fires a one-time Discord alert (deduped by trade ID, never repeats for the same trade) whenever the account-wide total is found over cap, plus a live "⚠ OVER CAP" row on the on-chart dashboard that appears while the violation persists and clears itself once resolved. Event-driven only, triggered by a position actually opening or an order actually being adopted — no periodic timer. Detection and notification only; nothing is auto-closed or auto-cancelled by this.
FIXEDBoth cBots (v1.22 / v2.28) — Custom Time Filter and Day Filter silently inert whenever Session Filter was off: The call site gated the entire IsValidSession() method — which both of these filters live inside — behind Enable Session Filter alone. Confirmed for real on a live FTMO account: Session Filter off, Custom Time Filter on with every day correctly configured 7am–10pm — a fresh order still armed at 23:00, since the method containing the time/day check was never even being called. Each of the three filters (Session/Time/Day) is now genuinely independent, matching what their separate toggles already implied they were.
ADDEDVEPX only (v1.23) — Optional Volume Confirmation, a second confirmation stage: EDGE EXH's own signal bar is fundamentally about exhaustion — low participation at the boundary — so requiring elevated volume on the signal bar itself would contradict the pattern's own premise. When Enable Volume Confirmation is on (default off), a fresh signal no longer arms an order immediately — it waits up to Confirmation Expiry Bars for a following bar to both close beyond the buffered target and show tick volume meaningfully above this symbol's own recent normal (mean + Volume Confirmation Multiplier × std dev, both computed over the same window — deliberately not split across two different sample sizes the way the indicator's own REJECTION-signal volume check does). Only once both land on the same bar does the real order get placed, through the exact same placement guards as the existing immediate-arm path.
FIXEDIndicator (v2.14) + VPDC (v2.31) — PDC cross confirmation didn't actually require the Entry Buffer: Both files' PDC cross check only ever required closing beyond bare PDC — the Entry Buffer was computed separately and applied only to where the resulting order/alert-reported entry sat, never to the confirmation condition itself. Confirmed for real: a trade could confirm on a close that barely ticked past PDC, then the order placed further out at PDC+Buffer regardless of whether price had genuinely continued that far. Both now require the close to clear PDC ± Entry Buffer as one combined condition — the same buffered level used both to confirm the cross and as the resulting target, one source of truth instead of two independently-computed numbers that could disagree. Real behavior change: fewer, later-confirmed signals than before on both files.
ADDEDIndicator (v2.15) — PDC Cross Alert shows the raw PDC value and buffer distance alongside Entry: e.g. "Entry: 1.38732 (PDC 1.38792 - 6.0p buffer)" — makes the v2.14 buffer directly verifiable from the alert itself without needing to separately check the dashboard.
ADDEDVPDC (v2.30) — Empty-bin boundary line ported from VEPX: Draws a line at the boundary between real volume and the empty-bin void, plus a "N empty (min X)" count label at each boundary, and optional profile High/Low reference lines — VPDC was already computing this data internally for its own empty-bin re-validation feature, it just never drew any of it on the chart. Purely a missing visualization; no change to trading logic.
NOTEAll three files — Temporary license check bypass (Indicator v2.13, VEPX v1.24, VPDC v2.29): Single-user right now, and the real check was failing hard on transient GitHub Gist rate-limiting (429 Too Many Requests) — especially likely when reloading many chart instances close together. The check fails closed by design (a network hiccup disables the whole file), which is correct once this is genuinely multi-user, but not worth the false-positive lockouts for one person. The real check is left fully intact underneath, gated behind a single bypass flag, ready to re-enable later.

What's New — Aug 2026 (VPDC v2.24, VEPX v1.18, Indicator v2.12)

Driven by a real InvalidRequest/"Nothing to change" alert flood on live GBPJPY and CADJPY positions, followed by three requested hardening features and one indicator display fix.

FIXEDBoth cBots (v1.15 / v2.21) — Break-even retry loop, unthrottled: Confirmed for real on CADJPY — a failing BE ModifyPosition call retried on every single tick with no backoff, generating an InvalidRequest flood for 2+ minutes straight. Now throttled to once every 2 seconds, with a wrong-side-of-price guard that skips the call entirely (rather than retrying) when the candidate SL can never succeed until price itself moves.
FIXEDBoth cBots (v1.15 / v2.21) — BE success not recorded for the trailing comparison: Confirmed for real on GBPJPY — right after BE succeeded, the manual-trailing block compared its next candidate SL against the stale, SDK-cached pos.StopLoss.Value instead of what BE had just actually set, and resubmitted the identical price the broker had already accepted — rejected every time as a no-op. BE success now updates _lastAppliedManualSl directly, closing the gap.
VEPX ONLYVEPX (v1.15) — Late-delivered fill event could move an already-trailed SL backward: OnPositionOpened blindly reset _beTriggered = false on every fill. Confirmed for real: when the FILLED event itself arrived late (after BE had already fired and trailing had already advanced the SL further), that blind reset re-ran BE and moved the SL backward to the original BE level. Now infers BE state from the position's actual current SL-vs-entry relationship instead of resetting unconditionally — same inference RecoverOpenPositionState already used. VPDC doesn't need this fix: it resets BE state at arm time, before fill, not in the fill handler.
ADDEDBoth cBots (v1.16 / v2.22) — SL-breach pre-fill order cancellation: A pending stop order previously had only two exits — a genuine fill, or Expiry Bars running out. Price could run straight through where the SL would sit once filled and keep going, with the order still live the entire time it took to expire. Now cancelled outright, every tick, the instant price crosses that specific order's own frozen SL level before the entry itself ever fills — direction-aware (watches Bid for a BUY stop's SL, Ask for a SELL stop's SL). No parameter toggle — always on, by design, since letting a stop order fill into an already-effectively-stopped-out trade isn't a configuration anyone would want.
ADDEDBoth cBots (v1.17 / v2.23) — Continuous adoption of untracked manual pending orders: A manually-placed, Comment-tagged pending order was previously only ever picked up at cBot restart (RecoverOpenPositionState) — placed while the cBot was already running, it was invisible to every cancellation path (dead time, blackout, expiry, empty-bin re-validation, SL-breach) until the next restart. A new check now runs every 90 seconds, scans for any Label/Comment-matched order not already under management, and adopts it into full management from that point on — Discord-alerted when it happens. Also fixed the same gap in restart recovery itself: it was never deriving the order's actual SL price (only distance), silently exempting even restart-recovered manual orders from the SL-breach check.
ADDEDBoth cBots (v1.18 / v2.24) — Discord alert titles now distinguish cBot vs. manual trades: Trade Filled and Trade Closed alert titles now read "cBot Trade Filled/Closed" or "Manual Trade Filled/Closed", derived from whether Label or Comment matched the order tag — makes it possible to tell which is which from the title alone when scanning a Discord channel. Cosmetic only; both sources are already managed identically.
FIXEDIndicator (v2.11) — EMPTY label now draws on every historical profile, not just the live one: The consecutive-empty-bin count itself was already computed correctly per profile, but the actual "EMPTY" text label only ever rendered for the current/live profile (pNum 0) — every historical profile's empty boundary bins showed nothing at all, even with Show Volume Labels on. Now draws on all Number of Profiles.
FIXEDIndicator (v2.12) — EMPTY label x-position on historical profiles: v2.11's fix reused the live profile's own label placement (8 bars right of that profile's end bar) for every profile. That placement only makes sense for the live profile, whose end bar is the last bar on the chart — 8 bars right lands in open space. A historical profile's end bar sits mid-chart, so the same offset landed the label inside the next, more recent profile's own candle window instead — confirmed visually, EMPTY labels on older profiles were drifting off to overlap unrelated, later price action. Historical profiles now anchor their EMPTY label directly at their own end bar, matching the existing High/Low label convention.

What's New This Round — StopLimit Resolved, Missing-SL Auto-Attach, Min Empty Bins Split

A [empty, filled, empty] pattern wrongly counted as 2. Fixed to walk from the true price extreme and stop at the first real volume, matching the underlying detection logic exactly.
ADDEDAll three files — Min Empty Bins split into High/Sell and Low/Buy: A single shared threshold couldn't compensate for a real structural bias: the profile's top bin is empty far more often than genuine exhaustion alone would explain, since volume is attributed by each candle's CLOSE price, not its full high/low range — whichever candle set the High almost never closed exactly there. ADDEDBoth cBots — Max Stop-Limit Slippage (x ATR): The fixed-pips version behaved very differently across symbols — confirmed for real when a live CADJPY order was cancelled by the broker itself (no cancel request from the cBot at all), since 5 fixed pips was a far tighter real cap there than intended. ADDEDVEPX — Live empty-bin count labels on the chart: The boundary line now shows the actual count right next to it (e.g. "2 empty (min 3)"), reusing the exact same count already computed for the line itself.
ADDEDVEPX — Opposing-signal alert: Fires once per open position if a genuine opposing-direction EDGE EXH appears while a trade is already open — purely informational, no automatic action. VEPX-only, since VPDC's PDC-confirmation requirement means a bare opposing signal isn't yet something VPDC itself would consider valid.
FIXEDBoth cBots — Chart redraw was bar-close-only: A manual chart refresh can re-index cTrader's own bar history, leaving profile lines/labels stale until the next bar close — up to a full hour once running on H1. Now also redraws from OnTick, throttled to once every 2 seconds.
ADDEDBoth cBots — Distance Unit Mode moved to General: Was buried inside Stop Loss despite being a global switch controlling calculations across two separate sections (Stop Loss and the entry-buffer group). Now sits at the top of the panel, visible as the global toggle it actually is.
ADDEDPine Script — Full parity pass: Ported the consecutive empty-bin fix, PDC tracking, PDC Cross Alert watch mechanism, Dead Time Filter (manual UTC window, since Pine has no broker-calendar equivalent), and structural SL/TP for EDGE EXH's alert. Section 01

What is VolumeEdge Pro?

VolumeEdge Pro is a Fixed Range Volume Profile (FRVP)Plots a horizontal histogram of traded volume over a fixed number of bars. Each horizontal bar = one price bucket (bin), width = volume at that price. Shows where institutional activity was concentrated. indicator for cTrader. It draws horizontal volume histograms on your chart and fires signals based on what the histogram bins show — not just where price is.

Core FRVP Levels

POC — POINT OF CONTROL

Highest volume price level

Most traded price bin. Acts as a magnet. Shown as a yellow solid line.

VAH — VALUE AREA HIGH

Upper value boundary

Price above VAH = bullish breakout zone. Shown as a green dotted line.

VAL — VALUE AREA LOW

Lower value boundary

Price below VAL = bearish breakdown zone. Shown as a red dotted line.

VA — VALUE AREA

Institutional activity zone

Contains your configured % of total volume (default 40%). Where most activity occurred.

Signal Types

POC TOUCH · MEAN REVERSION

Price returns to POC

Best in ranging marketsADX below 20. Price oscillating without clear directional trend. (ADX < 20). Bin confirmation: POC zone must show dominant side with sufficient ratio.

VA TRAP · MEAN REVERSION

Price re-enters value area

Trapped breakout traders reversing. Bin confirmation: POC must show correct directional dominance to confirm the level is holding.

EDGE EXHAUSTION · MOMENTUM

Stalls at profile boundary

Best in trending marketsADX above 25. Price moving directionally with institutional backing. (ADX > 25). v2.1: fires only when empty bins exist at boundary.

REJECTION · MOMENTUM

Wick + volume spike reversal

Wick into key level with volume spike, close pulls back. v2.1: LVN check added — thin boundary = stop hunt = suppressed.

Section 14 · New in v2.1

Bin-Based Signal Engine

★
Core principle shift in v2.1

Signals no longer fire based on price bar conditions alone. The horizontal histogram BINSEach horizontal bar in the FRVP histogram = one price bucket. Width = volume traded at that price. The bins are drawn from historical data — they don't change bar by bar. They show the settled reality of where institutions traded. confirm or suppress every signal. Price bar position is only the trigger to start reading the bins. The bins are the judge.

Why bins, not price bars?

Price bars are noisy — a wickThe thin line above/below a candle body. Represents the high/low price briefly reached but not sustained. A wick touch at a level with zero bin volume = stop hunt or random volatility, not institutional activity. can touch a level with zero volume. The histogram bins show you the settled reality of where institutions actually traded. A bin with zero volume means nobody traded there — that IS the signal.

Edge Exhaustion Logic

★
The Empty Bin Rule

EDGE EXH fires when at least 1 empty binA price bucket with TotalVols = 0. Means zero trades occurred at that price during the lookback window. Price briefly visited it but nobody was willing to trade there — instant rejection. The most objective exhaustion signal possible. exists at the profile boundary. An empty bin means price briefly visited that level with zero institutional activity — genuine exhaustion. This single rule, validated against 9 real chart examples, replaces all previous complex pattern logic.

What an empty bin means

18571 / 0 (IMB) — buyers pushed here
12801 / 2810 (IMB) — buyers dominant
[ empty bin ] ← nobody traded here
0 / 25998 (IMB) — seller wall
▼ EDGE EXH SELL fires — empty bin confirms buyer exhaustion at boundary

EDGE EXH SELL — fires when

At least 1 empty bin exists in the top boundary zoneThe outermost bins near the profile High. Scanned depth = BoundaryScanPct% of total bins. EURUSD: ~4 bins. BTCUSD: ~8 bins. If any of these are empty = price reached the High with zero institutional conviction. (near profile High). Price briefly touched that level with zero institutional interest = buyers had no conviction at the High.

EDGE EXH BUY — fires when

At least 1 empty bin exists in the bottom boundary zoneThe outermost bins near the profile Low. If any are empty = sellers pushed price to the Low but couldn't find anyone to sell to. The void below the Low means sellers had no conviction — price must reverse. (near profile Low). Price briefly touched that level with zero institutional interest = sellers had no conviction at the Low.

Gate Performance Audit

The [B] tag in recent outcomes is your gate performance reportEvery blocked signal shows in the analysis panel with a [B] tag and the outcome it would have had. Over time, patterns in [B] WIN vs [B] LOSS tell you if your gates are helping or hurting your edge.. Three scenarios:

SCENARIO 1 — Mostly [B] WIN rows

Gates are too strict

Good signals being filtered. Action: lower MinConfluenceGate from 2 to 1, or reduce CooldownBars, or check session filter hours for this symbol.

SCENARIO 2 — Mostly [B] LOSS rows

Gates are working perfectly

Bad setups being caught before they hurt you. Do not change anything — the gates are your edge.

SCENARIO 3 — Mixed [B] results

Look at which gate is blocking

If most [B] WIN are blocked by cooldown but [B] LOSS are blocked by confluence — confluence gate is good but cooldown is too aggressive. Reduce CooldownBars. Keep confluence at 2.

💡
Decision Rule

If blocked LOSSes > blocked WINs in total pips → gates net-positive, keep them.
If blocked WINs > blocked LOSSes in total pips → gates net-negative, loosen them.

Section 23 · Concept

What are Bins?

BinsShort for histogram bins — equal-width price buckets that divide the profile's price range. Each bin records how much volume was traded within that price slice. are the fundamental building blocks of the Fixed Range Volume Profile. The name comes from statistics — a histogram groups data into equal-width buckets called bins.

How bins are created

When you set a lookback of 24 bars on H2, the indicator reads every bar in that window and finds the overall High and Low. That price range is then divided into equal slices — one slice per bin:

What each bin stores

FieldMeaning
BuyVolTotal buy-side volume traded within this price slice. A bar where Close ≥ Open contributes its volume here.
SellVolTotal sell-side volume traded within this price slice. A bar where Close < Open contributes here.
TotalVolsBuyVol + SellVol. Used for width of the histogram bar.

Why bin size matters

Bin size = (High − Low) ÷ number of bins. More bins = finer resolution but noisier. Fewer bins = cleaner but loses precision at key levels.

The empty bin — the most powerful signal

An empty binTotalVols = 0. Price passed through this price level so quickly that zero volume was recorded. The market had zero interest in trading at this price. This is the strongest exhaustion signal — genuine price rejection. means TotalVols[b] == 0. Nobody traded at that price during the entire lookback window. Price visited that level briefly but the market had zero interest in transacting there — it was immediately rejected. This is the foundation of the EDGE EXH signal in v2.1.

💡
Think of it like an auction

Each price level is an auction. If nobody shows up to bid or offer at a price, that auction fails instantly. An empty bin = a failed auction = the market doesn't want to trade there = price must reverse.

Section 01

What is VolumeEdgeProSession?

VolumeEdgeProSession is a fork of the original VolumeEdgeProFlow indicator that replaces its continuously-sliding rolling lookback window with hard-reset, calendar-anchored periods instead — Daily, Weekly, or Monthly. Every other core mechanic — the FRVP profile itself, POC/VAH/VAL, the EDGE EXH signal, MA Cross, the PDC reference line — is carried over unchanged. The one thing that's genuinely different is what defines the start and end of a profile.

🎯
The core idea

The original VolumeEdgeProFlow's "Number of Profiles" setting tiles fixed-size chunks of bars backward from the current moment — profile 2 is exactly N bars before profile 1, regardless of what calendar day or week those bars actually fall on. VolumeEdgeProSession replaces that entirely: profile 1 is today's session (or this week's, or this month's), profile 2 is yesterday's complete session, and so on — each one a genuinely fresh calculation from its own anchor point, never a shifted continuation of the one before it.

Section 02

Session vs Rolling Lookback

ROLLING (original)

VolumeEdgePro Flow

Every bar close shifts the whole window forward by one bar. Profile boundaries drift continuously — "today's profile" at 9am and at 5pm cover a different, overlapping set of bars, not the same session.

ANCHORED (this fork)

VolumeEdgeProSession

Each profile is pinned to a real calendar boundary. "Today's profile" means the same thing at 9am and at 5pm — everything since this session's own reset, nothing more, nothing less.

💡
Why this matters for EDGE EXH specifically

EDGE EXH reads a profile's own High/Low boundary for empty bins. A rolling window's High/Low can shift bar-to-bar even when nothing structurally significant happened — a session-anchored profile's High/Low only changes when a genuinely new extreme is set within that same, fixed period. The boundary means the same thing all day, not a slightly different thing every bar.

Check this against your own broker's actual daily rollover if the reset doesn't land where you expect.

Off by default, so anyone already using the UTC field keeps their exact existing behavior.

Section 04

How Anchoring Works

Internally, every bar gets a computed "session key" — a date (adjusted for the reset hour, so a bar before the reset hour on its own calendar date is correctly treated as still belonging to the previous day's session) for Daily, that week's own Monday for Weekly, or that month's own 1st for Monthly. The profile's start (anchor) is found by walking backward from the current bar until the session key changes — that's the boundary.

Number of Profiles still controls how many historical periods are drawn (profile 1 = current, profile 2 = the previous complete period, and so on) — but each one is now a genuinely separate, real calendar period, not a fixed bar-count chunk. A Daily session's own bar count varies day to day depending on how the market actually traded; that's expected, not a bug.

💡
Confluence uses the same anchored boundaries

The Confluence Gate (how many profiles' own POCs cluster together) reads from these same session-anchored profiles, not a separate calculation — so a level's confluence score reflects genuine agreement across distinct trading days/weeks/months, not arbitrary overlapping chunks of the same continuous window.

Section 05

Cold-Start Gate

Minimum Bars Since Reset (default 10) blocks EDGE EXH from firing as a real, colored signal until a session has accumulated at least this many bars since its own reset.

⚠️
Why this exists

A freshly-reset session's own High/Low are, almost by definition, wherever price happened to be in the first few bars — that's immaturity, not genuine exhaustion. Without this gate, EDGE EXH could fire constantly in the opening minutes of every new session purely because the profile hasn't had time to develop real structure yet.

The profile itself, POC/VAH/VAL, and the chart drawing all still work normally during the cold-start window — only the signal's own fired/blocked status is affected. A blocked EDGE EXH during cold-start still shows as a gray label on chart, matching every other block reason (dead session, low confluence, and so on) — not treated as a separate, new visual state.

Section 06

PC (Previous Session Close) NEW

What used to be called PDC — Previous Day Close, always Daily regardless of chart — is now PC: Previous Session Close, matching whichever mode is actually active. On a Daily session it's yesterday's D1 close, same as before. On a Weekly session it's last week's own close; on Monthly, last month's.

🎯
Why the rename, not just new behavior

Once Session Mode could genuinely run Weekly or Monthly, a reference line still labeled "PDC" (Previous Day Close) would have been actively wrong on those charts — showing a Weekly close but calling it a daily one. Internal identifiers (ShowPdcLine, the underlying field names) deliberately kept their old names — only the displayed text, on-chart label, and dashboard row changed from PDC to PC.

PC still feeds the same things it always did: the dashboard's PC row, the PEP modifier tag (+ PC / - PC WARN), and now also Tier 3's own confirmation target (see below) — genuinely new, not something PDC ever did in this indicator.

Section 07

The single EDGE EXH alert this indicator always had is now Tier 1 of three, each with its own Discord/Telegram destination and its own reason to exist. All three trace back to the same underlying EDGE EXH event — they're not three independent signal types.

TIER 1

Fires immediately, same bar, the moment EDGE EXH passes every existing gate (empty bins, cold-start, confluence, cooldown, session filter). Exactly what this indicator always alerted on — now explicitly tagged and routed to its own channel rather than being the only channel.

TIER 2

Checks backward first — a matching-direction MA cross already within Backward Cross Lookback confirms immediately. If nothing's found, a forward watch arms instead of the moment passing, waiting up to MA Cross Forward Expiry (bars) for a fresh cross. Off by default (Enable MA Cross Confirmation Alert).

TIER 3

💡

A single EDGE EXH can produce Tier 1 alone, Tier 1 plus one of the others, or all three — Tier 3 doesn't wait for Tier 2 to resolve first, and vice versa. Both watches arm at the same moment Tier 1 fires, each running its own independent clock.

⚠️
Expiry bars count from AFTER the signal bar, not including it

EDGE EXH fires on bar 0 and arms a watch with a 5-bar expiry — the watch gets bars 1 through 5 (five genuine chances) to see a confirming close, expiring only once bar 6 closes without one. The signal's own bar is never itself a chance to confirm, since the watch doesn't exist yet at the moment that bar is being evaluated.

🎯
A watch survives a session reset

If EDGE EXH fires near the end of one session and the confirming cross happens after a new session has already started, the watch still resolves correctly — it isn't touched by session-reset logic, Tier 3's target price is frozen permanently at arm time (never silently updates to the new session's own PC), and Tier 2's MA values are fully continuous, with no awareness of session boundaries at all. The one real interaction: a fresh EDGE EXH in the same direction from the new session will overwrite the still-pending watch — the standing "most recent signal wins" rule across every tool in this suite.

Section 01

What is POC Magnet?

POC Magnet is based on one of the most reliable principles in volume analysis: price always returns to the Point of Control. The POCPoint of Control — highest-volume price in the profile. Where most institutional activity occurred. When price moves away, it creates an imbalance the market constantly works to resolve by returning. is where institutions built their positions. When price drifts far away, it creates an imbalance that resolves by returning.

Your job: identify when price is far from POC, determine which direction it needs to travel, and position yourself on that journey.

🧲
The magnet principle

A D1 POC sitting 40+ pips away is a magnet with enormous gravitational pull. The further price is from POC, the higher the probability it returns. D1 POC = strongest magnet. H2 POC = medium-term mid-target. M30 POC = entry guide.

Section 02

Why POC Always Pulls

REASON 01

Mean Reversion

Price oscillates around equilibrium. POC is the most recent equilibrium. Extended moves always self-correct. Statistical, not opinion.

REASON 02

Institutional Memory

Large players who built positions at POC defend that level. When price returns they add or take profits — both push price back toward POC.

REASON 03

Unfilled Orders

Naked POCsPrior session POCs price has never revisited. Unfilled institutional orders still waiting there. Every session without a return increases the pull — until it snaps back violently. from prior sessions = unfilled institutional orders. The longer price stays away, the stronger the eventual pull.

Section 01

What is VEPFPT?

VolumeEdgePro FPT (Flow Profile Trader) is a single cAlgo cBot that consolidates and fully replaces the five retired cBots — VPDC, VSPC, VMAX, VSMA, and VEPX — into one codebase with three independently-togglable trigger paths, instead of five separate single-strategy bots that each had to be run, licensed, and maintained on its own.

🎯
Why consolidate

All five retired bots shared the same underlying EDGE EXH detection, FRVP profile math, sizing, structural SL, BE/trailing, and account-risk code — they only differed in what, if anything, had to confirm EDGE EXH before an order was placed. Running them as five separate files meant five separate licenses, five separate parameter panels to keep in sync, and the same bug fix having to be ported five times. FPT (and its session-anchored sibling, VEPSPT) folds all of that into one bot per profile-anchoring style, with the confirmation choice itself exposed as three parameters instead of five different files.

FPT uses a rolling, fixed-bar lookback window for its FRVP profile — the same no-session-concept approach VPDC, VMAX, and VEPX used. Its sibling, VEPSPT, instead hard-resets its profile at a calendar-anchored session boundary (Daily/Weekly/Monthly), the approach VSPC and VSMA used. Other than profile anchoring, the two bots mirror each other's architecture closely — see the Comparison Table tab for a full side-by-side.

Section 02

Trigger Logic — 3 Independent Paths

EDGE EXH detection, chart history, and the dashboard always run, regardless of which (if any) trigger paths are enabled — they're diagnostic/visual by default. Placing a real order requires opting into at least one of the three paths below; all three default OFF.

PATH 1

EDGE EXH Alone

Immediate entry on the same bar as the signal, no confirmation wait. A real stop order is placed the instant EDGE EXH fires and clears whichever of the three optional gates below are enabled. Replaces VEPX.

PATH 2

PC Cross Confirmation

EDGE EXH arms a watch; a later candle closing back across PDC (FPT has no session concept, so "PC" here always means Previous Day Close) within EDGE EXH Watch Expiry bars confirms it. A real order is then placed, with Stop Order Limit (Expiry) bars to fill. Replaces VPDC.

PATH 3

MA Cross Confirmation

EDGE EXH plus a matching-direction moving-average cross confirms it — checked both backward (did a cross already happen in the last Backward Cross Lookback bars) and forward (does one happen within MA Cross Confirmation Expiry bars after). Replaces VMAX.

💡
All three default off, and all three can run together

Nothing stops enabling two or three paths on the same instance — a single EDGE EXH signal can be watched by PC Cross and MA Cross at the same time, and whichever confirms first wins the slot for that direction (see Arming Lock below). EDGE EXH Alone is exempt from that lock and can fire independently even while a watch is pending on the other two paths, subject only to the Symbol-Wide Open-Position Gate.

Section 03

Arming Lock

MA Cross Confirmation and PC Cross Confirmation compete for the same-direction pending slot only — a Buy-side watch under one path blocks a second Buy-side watch from the other path from arming at the same time, and whichever path's watch confirms first takes the slot. The slot releases the moment that direction's pending state clears for any reason — a cancel, an expiry, or a fill — at which point either path is free to arm a fresh watch in that direction again.

💡
EDGE EXH Alone is exempt entirely

Because it places an order immediately with no watch-and-wait phase, EDGE EXH Alone never competes for the arming lock — it can fire on the same bar even while MA Cross or PC Cross has an active watch pending in the same direction. The only thing that can still block it is the Symbol-Wide Open-Position Gate below.

Section 04

Symbol-Wide Open-Position Gate

Before any of the three paths places a new order, FPT checks for any open position already on that symbol — from this bot, from its sibling VEPSPT if both happen to be running on the same symbol, or from a plain manual trade with no label or comment filter applied at all. If one exists, every new order from all three paths is blocked.

⚠️
Watch/arm state keeps running on its own clock

This gate blocks new orders, not the watch/arm state machine itself — a PC Cross or MA Cross watch that's already counting down its expiry keeps counting down normally even while this gate is active. If the open position closes before the watch expires and a cross still confirms in time, the order still places then, as normal.

Section 05

EDGE EXH Alone Gates FPT only

Three optional gates, all OFF by default, that apply only to the EDGE EXH Alone path. Each one delays when the order actually gets placed — none of them change the frozen target, SL, or sizing once the gate clears. VEPSPT does not have these three gates — its EDGE EXH Alone path has only the plain enable toggle, no extra filters (see Known Limitations).

GATE 1

Volume Confirmation

A later bar (within Confirmation Expiry Bars) must close beyond the frozen target and print tick volume above this symbol's recent mean + Volume Confirmation Multiplier × standard deviation, measured over Volume Confirmation Window bars (0 = use the dynamic profile lookback instead of a fixed window).

GATE 2

PDC Distance Filter

A floor, not a confirmation wait: only acts on the signal if it's already at least Min PDC Distance (x ATR) away from PDC at the moment EDGE EXH fires. Filters out signals sitting too close to PDC to be a meaningful exhaustion read.

GATE 3

Extreme Stall Gate

If the very next bar extends price past the signal bar's own profile extreme (the level EDGE EXH fired at), the signal is abandoned — a genuine exhaustion read shouldn't immediately get taken out by more of the same move.

Section 06

Position Sizing, Structural SL, Break-Even & Trailing

The stop loss is structural, anchored to the profile boundary the EDGE EXH signal actually fired against: SL = profile Low − (ATR × SL Buffer) on a Buy, or profile High + (ATR × SL Buffer) on a Sell. Max SL Distance is a sanity cap — a structural distance wider than this skips the trade entirely rather than forcing an oversized risk to fit it.

FIXED LOT

Position Sizing Mode = FixedLot

Every trade opens at Lot Size, regardless of stop distance.

PERCENT RISK

Position Sizing Mode = PercentRisk

Lot size is calculated backward from Risk % Per Trade (or, with Auto-Divide Daily Risk on, from Target Daily Risk % ÷ Trades Per Day Budget) and the trade's own structural SL distance. Max Lot Size caps it — 0 auto-derives the sizing basis from Max SL Distance instead of the actual signal SL, guaranteeing realized risk never exceeds target.

Once price moves in favor by Break-Even Trigger (x Risk) × the initial risk distance, SL moves to entry + BE Lock Profit — a small real profit, not exactly entry. From there, Trailing Stop Mode picks how the stop advances: Manual (default) is a tick-tolerant, throttled per-tick loop run entirely by this cBot's own code; Native hands off once to cTrader's own trailing-stop flag with a single ModifyPosition call, after which cTrader itself manages the stop and this cBot doesn't touch it again for that trade.

Because FPT's profile is a rolling, fixed-bar lookback window rather than a hard-reset session, a historical signal can drift from what the live window would show by the time you look back at it later — the window has simply moved on. This is an inherent trade-off of rolling-profile design, not a defect. It was fixed this cycle for historical EDGE EXH signal logging/counting accuracy in the sibling non-cBot indicator (VEPF v2.28) — but that fix is about backward-looking displayed history there, not about this cBot's own live trading: FPT's live detection always evaluates against the current rolling window by design, every bar, so live entries are never affected by this drift.

Section 01

What is VEPSPT?

VolumeEdgePro SPT (Session Profile Trader) is a single cAlgo cBot that consolidates and fully replaces the session-anchored retired cBots — VSPC and VSMA — into one codebase with the same three independently-togglable trigger paths as its rolling-profile sibling, VEPFPT.

🎯
FPT and SPT mirror each other

SPT and FPT share essentially the same architecture — EDGE EXH detection, the three trigger paths, sizing, structural SL, BE/trailing, account-risk code, alerts — and differ in exactly one place: how the FRVP profile is anchored. FPT uses a rolling, fixed-bar lookback window with no session concept at all. SPT instead hard-resets its profile at a calendar-anchored session boundary — Daily, Weekly, or Monthly — so each session gets its own frozen, from-scratch profile rather than a continuously sliding one.

Because each session's profile is frozen the moment that session ends, SPT doesn't inherit FPT's rolling-window drift (see FPT's Known Limitations) — but its EDGE EXH Alone path also doesn't inherit FPT's three optional gates (see Known Limitations below).

Section 02

Trigger Logic — 3 Independent Paths

Identical to FPT: EDGE EXH detection, chart history, and the dashboard always run regardless of toggles. All three paths default OFF.

PATH 1

EDGE EXH Alone

Immediate entry on the same bar as the signal, no confirmation wait. Only the plain enable toggle on SPT — none of FPT's three optional gates. Replaces VSPC's EDGE-EXH-only behavior and VSMA's equivalent.

PATH 2

PC Cross Confirmation

EDGE EXH arms a watch; a later candle closing back across the Previous Session Close (PC) — auto-detected from the active session boundary as Daily, Weekly, or Monthly — within EDGE EXH Watch Expiry bars confirms it. Replaces VSPC.

PATH 3

MA Cross Confirmation

EDGE EXH plus a matching-direction MA cross, checked backward and forward exactly as on FPT. Replaces VSMA.

Section 03

Arming Lock

Identical mechanism to FPT: MA Cross and PC Cross compete only for the same-direction pending slot, first to confirm wins, and the slot releases the moment that direction's pending state clears for any reason. EDGE EXH Alone is exempt from this lock entirely and can fire immediately regardless of what the other two paths are doing.

Section 04

Symbol-Wide Open-Position Gate

Identical to FPT: any open position on that symbol — this bot, its sibling FPT if both run on the same symbol, or a plain manual trade with no label/comment filter — blocks every new order from all three paths. Watch/arm state keeps running on its own clock regardless.

Section 05

This is a genuine calendar-anchored reset, not a rolling window — and by design it carries no cold-start gate: the first bar of a fresh session starts building a fresh profile from nothing, immediately.

Section 01

What is VEPF?

VolumeEdgePro Flow (internal tag VEPF) is a free TradingView Pine Script indicator — a direct port of the cTrader VolumeEdgeProFlow engine's rolling, fixed-bar-lookback profile design onto Pine. It renders the same Fixed Range Volume Profile (FRVP) boxes, POC/VAH/VAL lines, and EDGE EXH exhaustion detection as its cTrader parent, plus the full three-tier Discord/Telegram alert pipeline this suite's cTrader side proved out first.

🎯
Deliberately free, deliberately scoped down

VEPF deliberately excludes the two things that make the cTrader VolumeEdgeProFlow indicator something you'd pay for: the remote account-based License System, and the AI Bias Analysis calls to Claude/Gemini/DeepSeek. Pine has no account/network layer to gate a license against, and no natural way to make a provider-API call of that kind from inside the sandbox — both were cut rather than half-built. Everything else — the profile engine, EDGE EXH, Confluence Gate, MA Cross, PC Cross Alert, D1 Dashboard — is a genuine, working port, not a stripped-down demo.

The underlying script file carries its own version history back to vep.pine v2.3 — the original, pre-rename Pine port this suite was built from. VEPF's own numbering restarts at v1.0, independent of both vep.pine's old v2.x numbering and the cTrader indicator's own v2.x numbering, which this port now diverges from under its own name.

Section 02

Relation to FPT and VEPS

VEPF mirrors the cTrader cBot VEPFPT's rolling-profile logic — same lookback window, same EDGE EXH detection, same Confluence Gate math — but VEPF is an indicator, not a trading bot: there is no order-placement call anywhere in this script, structurally. It can alert, it cannot trade.

VEPF (this tab)

Rolling, continuous lookback

Every bar close shifts the whole profile window forward by one bar. Mirrors cTrader FPT's anchoring style, and vep.pine's own original design before the session-anchored fork existed.

VEPS (sibling Pine tab)

Session-anchored, hard reset

Hard-resets at a calendar boundary — Daily/Weekly/Monthly/Auto, plus manual Quarterly/Half-Year/Yearly. Mirrors cTrader SPT's anchoring style. See the VEPS · TV tab.

This is the exact same rolling-vs-session split that separates VEPFPT from VEPSPT on the cTrader side — see the Comparison Table tab for the full four-way (now six-way, counting both Pine ports) breakdown.

Section 04

EDGE EXH Detection

EDGE EXH is the shared exhaustion signal across every tool in this suite, Pine included: a candle's wick touches the profile's own High or Low boundary, the touch is a genuine rejection (wicks through the boundary but closes back inside it), and the boundary's own empty-bin count meets the configured minimum — Min Empty Bins (High/Sell Side) (default 3) and Min Empty Bins (Low/Buy Side) (default 2), scanned over the top/bottom Boundary Scan Window (% of bins) (default 15%) of the profile.

⚠️
A rolling profile's boundary genuinely drifts bar to bar

Unlike VEPS's closed, calendar-anchored sessions, VEPF's profile High/Low can shift on every single bar close even when nothing structurally significant happened — this is an inherent property of the rolling-window design, not a defect. Historical EDGE EXH color-freezing (see Known Limitations) exists specifically to stop that live drift from retroactively repainting a past signal's own displayed color.

Section 05

Confluence Gate VEPF only

VEPF's Signal Gate requires two independent conditions: gateVolOk (the Volatility Filter — ATR above Min ATR (Pips)) and gateConfOk (Confluence — at least Min Confluence to Open Gate historical profiles' own POCs clustering at the same price). gateOpen = gateVolOk and gateConfOk.

⚠️
VEPS does not have this gate

VEPF's sibling, VEPS, removed cross-profile confluence entirely when it ported to session anchoring — comparing POCs across N fixed-bar rolling segments doesn't map cleanly onto variable-length calendar sessions. VEPS's own Signal Gate runs on the Volatility Filter alone: gateOpen = gateVolOk. Confirmed directly in both scripts' own source — this is a genuine feature difference, not an oversight on either side.

confluenceScore counts how many of the Number of Profiles historical segments have a POC within the same price bin as the live profile's own POC, and is deliberately excluded from the historical color-freeze fix below (see Known Limitations) — it has no genuine continuous per-bar history to offset against, since it is itself only ever recomputed live.

Section 06

Three-Tier Alert System

The same three-tier Discord/Telegram pipeline proven on the cTrader side and on VEPS's own Pine port first, ported here in full. All three trace back to the same underlying EDGE EXH event.

TIER 1

Bare EDGE EXH

Fires immediately, same bar, once EDGE EXH clears every existing gate (empty bins, Confluence, Volatility Filter, cooldown, dead time). Tagged "TIER 1 | Fixed Bar Profile" in its Discord/Telegram title — the "Fixed Bar Profile" tag is how this rolling-window port distinguishes itself from VEPS's "Session Profile" tag in a shared alert channel.

TIER 2

+ MA Cross Confirmation

Checks backward first — a matching-direction MA cross already within Backward Cross Lookback bars confirms immediately. If nothing's found, a forward watch arms instead, waiting up to MA Cross Forward Expiry (bars) for a fresh cross. Off by default (Enable MA Cross Alert (Tier 2)).

TIER 3

+ PDC Cross Confirmation

Arms on a fired EDGE EXH, freezing PDC + an ATR buffer as the confirmation target at that exact moment. Waits up to PDC Alert Expiry (bars) for a later close to actually cross it, requiring the close land past PDC ± PDC Alert Entry Buffer (x ATR), not bare PDC. On by default (Enable PDC Cross Alert).

💡
Reverse-signal invalidation

A fresh EDGE EXH in the opposite direction silently cancels the other side's still-pending Tier 2 (MA) or Tier 3 (PDC) watch — matching the cTrader indicator's own v2.26 addition, already proven on VEPS's Pine port before being carried over here.

⚠️
Repeat-fire fix is already included

An earlier version of this pattern (on VEPS, and latently in vep.pine before this file existed) could re-find the same old signal bar every bar once price was already past PDC, re-arming and re-firing with a drifting entry/buffer. VEPF tracks the last signal bar that armed a watch per direction (pdcLastArmedBarBuy/Sell) and refuses to re-arm off that same bar twice — fixed proactively here as part of this script's original build, not left for a future bug report.

Section 07

Alert Time/Day Filter & Dead Time Filter

Enable Custom Time Filter gives each weekday its own Start/End Hour pair (14 parameters total), optionally read in local time via Use Local Time for Filters + Time Zone Offset (UTC+), plus an independent Enable Day Filter with its own per-day Alert[Day] toggle. Both default to no restriction. This gates only whether a confirmed Tier 1/2/3 signal's alert actually fires — detection and the dashboard stay fully visible outside the window.

⚠️
Dead Time Filter is a manual UTC window on Pine, by necessity

Pine has no broker-calendar equivalent to read real market hours from, unlike the cTrader side's Symbol.MarketHours. Enable Dead Time Filter + Dead Time Start/End Hour (UTC) (default 21–22) is a manual, hand-set UTC window instead — the same deliberate trade-off already disclosed for the cTrader indicator's own Pine-parity changelog entry. Set this to match your own instrument's actual illiquid hours.

Section 08

Discord, Telegram & Output Format

Alert Output Format picks Discord or Telegram — one format per alert instance, since Pine's alert() fires one JSON payload to whichever single webhook URL is set in TradingView's own Create Alert dialog, with no way to pick a destination at runtime. buildAlertJson() builds either Discord's embed JSON or Telegram's {"chat_id":...,"text":...} shape from the same title/description, shared by all four Tier 1/2/3 alert call sites.

💡
Want both Discord and Telegram at once?

Add the indicator to the chart twice (or create two separate alerts from the one script), one set to each format — each with its own webhook URL / Telegram Chat ID. There is no single-script way to fire two differently-shaped alert bodies from one alert() call.

Telegram Chat ID and optional Telegram Topic ID (for landing in one specific topic thread of a supergroup, Telegram's message_thread_id) are both in the same Discord Alerts group.

Known Limitations

⚠️
v1.1's frozen-color fix was itself wrong — corrected in v1.2

EDGE EXH labels need a frozen, point-in-time color so a historical signal's own displayed gate/cooldown/dead-time state doesn't retroactively repaint as today's live state drifts. v1.1 tried to fix this by caching each bar's verdict the first time it was evaluated — but that caching sat inside a barstate.islast-gated block, which only runs once per full calculation pass, not once per historical bar as the script walks through history. On a fresh load/reload, every pre-existing historical bar's "first cache encounter" happened in that same single pass, baking in today's live gate/cooldown/dead-time state for all of them at once — the exact bug it was trying to fix, just hidden behind a map instead of removed.

🎯
v1.2 — fixed properly, with true per-bar series offsets

No caching at all: the signal-OK verdict (gate/cooldown/dead-time) now reads gateVolOk[b]/onCooldown[b] — genuine per-bar series computed unconditionally every bar, so offsetting by b correctly retrieves that bar's own true historical value, stable across any reload. EDGE EXH's own empty-bin verdict is recomputed per touch via calcProfile(s + b, e + b), shifting the window's offsets back by b to recover the exact profile composition as it stood when bar b was the newest bar. Confluence is deliberately excluded from this frozen check — it has no real continuous per-bar history to offset, being itself only ever recomputed live.

⚠️
v1.3 — v1.2's own fix caused a new runtime error, now fixed

v1.2's variable-offset series reads (gateVolOk[b], onCooldown[b], time[off] inside inDeadTimeAt, and open[i] inside calcProfile) triggered RE10143 — "requested historical offset beyond historical buffer's limit" — at higher Number of Profiles settings (5+). Root cause: Pine only auto-sizes a series' lookback buffer from constant-offset usage elsewhere in the script; a variable-offset read on a series with no explicit buffer declaration silently defaults to a small size (observed: 137 bars), regardless of how far the profile math actually needs to reach. Fixed by declaring max_bars_back(..., 4999) explicitly for open/time/gateVolOk/onCooldown — high/low/close/volume already had it.

💡
Dead Time Filter has no broker-calendar equivalent in Pine

Pine cannot read a real market-hours calendar the way the cTrader side's Symbol.MarketHours does — the Dead Time Filter here is a manual, hand-set UTC window instead. Same disclosed trade-off as the cTrader indicator's own Pine-parity changelog note.

Section 01

What is VEPS?

VolumeEdgePro Session (internal tag VEPS) is a free TradingView Pine Script indicator — a direct port of the cTrader VolumeEdgeProSession engine's session-anchored profile design onto Pine. It replaces a continuously-sliding rolling lookback with hard-reset, calendar-anchored periods — Daily, Weekly, or Monthly — while carrying over EDGE EXH detection, the three-tier Discord/Telegram alert pipeline, and (as of v2.07) the D1 Direction Dashboard.

🎯
Deliberately free, deliberately scoped down

Same exclusions as its sibling VEPF: no remote account-based License System, and no AI Bias Analysis calls to Claude/Gemini/DeepSeek — Pine has no account/network layer to gate a license against, and no natural way to make a provider-API call of that kind from inside the sandbox. Everything else — session anchoring, EDGE EXH, MA Cross, PC Cross Alert, D1 Dashboard — is a genuine, working port.

This port was built directly from vep.pine v2.3 (the original rolling-window Pine script, per direct instruction, after two earlier from-scratch attempts produced a broken, undifferentiated profile) rather than from VEPF — vep.pine's own proven profile engine, Discord alert JSON format, cooldown, dead-time filter, MA Cross plotting, and PDC Cross Alert state machine were kept intact and modified only where session-anchoring required it.

Section 02

Relation to SPT and VEPF

VEPS mirrors the cTrader cBot VEPSPT's session-anchored logic — same Daily/Weekly/Monthly reset mechanism, same EDGE EXH detection — but VEPS is an indicator, not a trading bot: there is no order-placement call anywhere in this script, structurally. It can alert, it cannot trade.

VEPS (this tab)

Session-anchored, hard reset

Profile 1 is today's session (or this week's/month's); profile 2 is yesterday's complete session, and so on — each one a genuinely fresh calculation from its own anchor point. Mirrors cTrader SPT's anchoring style.

VEPF (sibling Pine tab)

Rolling, continuous lookback

Every bar close shifts the whole profile window forward by one bar — no session concept. Mirrors cTrader FPT's anchoring style. See the VEPF · TV tab.

This is the exact same rolling-vs-session split that separates VEPFPT from VEPSPT on the cTrader side — see the Comparison Table tab for the full breakdown across all six tools now in the suite.

Section 04

How Anchoring Works

The variable name effectiveLookback is deliberately kept from VEPF/vep.pine — every downstream consumer (calcProfile() calls, the PC line, the dashboard's LOOKBACK row) keeps working unchanged; only what feeds into it changed. It's now computed as effectiveLookback = min(barsSinceReset + 1, Max Session Length) — the live session's own true elapsed bar count, capped by Max Session Length (bars, safety cap) (default 400) rather than a fixed, hardcoded-per-timeframe window.

Number of Sessions to Show (default 1, max 5) controls how many historical periods draw. getSessionOffsets(pNum) resolves session pNum (0 = live, 1 = previous completed session, 2 = the one before that, …) into calcProfile()'s own offset arguments by walking sessionStartBars — an array tracking each session's actual start bar as it happens — falling back to "not valid yet" once the chart's own history runs out.

💡
Max Session Length × Number of Sessions is a genuine buffer guarantee, not a guess

Number of Sessions is capped at 5 (was 20) and Max Session Length at 400 (was 2000) specifically so their product (5 × 400 = 2,000) exactly matches this script's own max_bars_back(..., 2000) declaration — a real mathematical guarantee against the historical-offset runtime error the uncapped 20 × 2000 combination could otherwise have exceeded.

Section 05

Cold-Start Gate

Min Bars Since Session Reset (cold-start gate) (default 5, min 0) blocks EDGE EXH from firing as a real, colored signal until a session has accumulated at least this many bars since its own reset — reads barsSinceReset directly.

⚠️
Why this exists

A freshly-reset session's own High/Low are, almost by definition, wherever price happened to be in the first few bars — that's immaturity, not genuine exhaustion. Same reasoning as the cTrader indicator's own cold-start gate, just a lower default (5 vs 10 bars) in this port.

Section 06

EDGE EXH Detection

The shared exhaustion signal across every tool in this suite: a candle's wick touches the profile's own High or Low boundary, the touch rejects (wicks through, closes back inside), and the boundary's own empty-bin count meets Min Empty Bins (High/Sell Side) (default 3) / Min Empty Bins (Low/Buy Side) (default 2), scanned over Boundary Scan Window (% of bins) (default 15%).

💡
Closed sessions' boundaries never drift — this is what the v2.06 fix exploits

Unlike VEPF's continuously-sliding rolling window, a session-anchored profile's High/Low only changes while that session is still live — once closed, its boundary is permanently fixed. This genuine structural difference is exactly why v2.06's fix (see Known Limitations) could reuse closed sessions' already-correct data directly, rebuilding only the still-open session's own window per touch bar.

Section 07

No Confluence Gate — Volatility Filter Alone VEPS difference

VEPS's Signal Gate is gateOpen = gateVolOk — the Volatility Filter alone (ATR above Min ATR (Pips)). Confirmed directly in the Pine source.

⚠️
Cross-profile confluence was removed, not ported, when this fork anchored to sessions

VEPF's Confluence Gate compares POCs across N fixed-bar rolling segments — a concept that doesn't map cleanly onto variable-length calendar sessions, where each session's own bar count varies day to day. Rather than guess at an untested replacement, this port's own header documents the decision explicitly: "worth building a real cross-session version later if wanted — not attempted here." confluenceScore is kept in the code as a fixed value (always 1, never computed) purely so the dashboard's existing Confluence display row and alert payload's d1Ctx/flipCtx fields keep working without a structural rewrite.

Section 08

Three-Tier Alert System

The same three-tier Discord/Telegram pipeline as VEPF and the cTrader indicator — all three trace back to the same underlying EDGE EXH event.

TIER 1

Bare EDGE EXH

Fires immediately, same bar, once EDGE EXH clears the Volatility Filter, cooldown, and dead-time gates. Tagged "TIER 1 | Session Profile" in its Discord/Telegram title — distinguishing it from VEPF's "Fixed Bar Profile" tag in a shared alert channel.

TIER 2

+ MA Cross Confirmation

Checks backward first — a matching-direction cross already within Backward Cross Lookback bars confirms immediately — then arms a forward watch for up to MA Cross Forward Expiry (bars). Off by default (Enable MA Cross Alert (Tier 2)). Reports Entry/SL/TP/Empty Bins since v2.01, matching Tier 3.

TIER 3

+ PC Cross Confirmation

Arms on a fired EDGE EXH, freezing PC + an ATR buffer as the confirmation target. Waits up to PC Cross Expiry (bars) for a confirming close past PC ± PC Alert Entry Buffer (x ATR). On by default (Enable PC Cross Alert (Tier 3)).

⚠️
MA WATCH (T2) row can be up to one bar stale — disclosed directly in this file's own header

Tier 2's own section runs after the dashboard renders, in this script's top-to-bottom execution order — so the MA WATCH row can show the previous bar's state rather than the current bar's freshest update. Moving Tier 2 earlier would also require moving Tier 1's own trigger variables (which Tier 2's arming depends on), a much larger restructure of proven detection logic than this lag justifies. PC WATCH (T3) does not have this issue, on either Pine or cTrader — this is the exact same caveat already disclosed in the cTrader indicator's own Known Limitations for its Pine port.

🎯
Reverse-signal invalidation

A fresh EDGE EXH in the opposite direction silently cancels the other side's still-pending Tier 2/Tier 3 watch, decoupled from Enable Discord Alerts so a contradicted watch stops counting down regardless of whether alerts happen to be on — matches the cTrader indicator's own v1.21 addition.

Alert Time/Day Filter & Dead Time Filter

Enable Dead Time Filter + Start/End Hour (UTC) (default 21–22) is a manual, hand-set window instead — the same deliberate trade-off already disclosed for the cTrader indicator's own Pine-parity changelog entry, and identical to VEPF's own version of this same note.

Known Limitations

⚠️
v2.04/v2.05 — the same underlying retroactive-repaint bug as VEPF's v1.1, fixed wrong twice before v2.06 got it right

v2.04 froze EDGE EXH's empty-bin verdict in a cache the first time each bar was evaluated, to stop a live session's still-open profile from retroactively flipping a past touch's label from colored to gray as the session filled in. Confirmed from a live EURUSD chart. v2.05 found the same bug one layer deeper — the signal-OK verdict (gate/cooldown/dead-time) was deliberately left live, and confirmed wrong from two screenshots of the same chart taken minutes apart: every EDGE EXH label on screen, including ones from already-closed historical sessions, flipped from colored to gray at once purely because cooldown had gone active on the CURRENT bar. v2.05 froze that too, the same caching way.

⚠️
v2.06 — both caches were themselves the wrong fix, confirmed via an identical bug report on VEPF

The whole EDGE EXH label loop runs inside if barstate.islast, which executes once per full calculation pass, not once per historical bar as the script walks through history. On a fresh load/reload, every historical bar's "first cache encounter" happened in that same single pass, baking in today's live state for all of them at once — exactly the bug v2.04/v2.05 were trying to fix, just hidden behind map.contains()/map.put() instead of removed.

🎯
v2.06 — fixed with a session-aware split, no caching needed at all

The signal-OK verdict is now computed per touch bar via genuine continuous per-bar series offsets (gateOpen[b], onCooldown[b], the new inDeadTimeAt(b)) — valid because those series are computed unconditionally on every bar. The empty-bin verdict is recomputed per touch bar from calcProfile(), but differently depending on whether the session is still open or already closed: for the still-open live session (pNum==0), whose near edge keeps sliding forward every bar, via calcProfile(s, b); for an already-closed session (pNum≥1), whose boundaries are fixed absolute bar indices and never drift, by directly reusing the already-correct volume data from the outer calcProfile(s, e) call — no recompute needed, since those profiles are permanently fixed once their session ends. This closed-session shortcut has no VEPF equivalent, since VEPF's rolling profiles never have a genuinely "closed" boundary to reuse.

💡
Dead Time Filter has no broker-calendar equivalent in Pine

Same disclosed trade-off as VEPF and the cTrader indicator's own Pine-parity note — a manual, hand-set UTC window stands in for a real market-hours calendar.

FAQ

Frequently Asked
Questions

The questions that came up most across real forward-testing — with the actual reasoning, not just the short answer.

Order Placement

Why did my StopLimit order get cancelled, or show a "Label mismatch"?

PlaceStopLimitOrder's basic call doesn't set the Label at all, on its own — confirmed for real on multiple live fills (a blank Label on the resulting order) back when this history was with the retired cBots. Both VEPFPT and VEPSPT use the correct extended overload (confirmed via an actual compile error, not just documentation), so this should be rare now. A safety net still watches for it as a defensive fallback regardless — even a compiler-confirmed fix doesn't guarantee every runtime case behaves exactly as expected.

💡
Three possible outcomes if it happens

STOP LIMIT LABEL MISMATCH — mismatch caught, cancel succeeded, no position ever opened. UNTRACKED POSITION OPENED — the cancel lost a race against a fast fill; a real position exists but is invisible to BE/trailing/daily-loss/concurrent-trade counting, so an emergency SL gets attached and this needs manual monitoring. LABEL MISMATCH, RETRYING CANCEL — the cancel failed for a reason other than "already filled" (often a transient PENDING_EXECUTION rejection, confirmed via the broker Journal to often resolve on its own within milliseconds) — the cBot keeps retrying automatically every 15 seconds.

Order Placement

Should I use StopOrder or StopLimit?

StopOrder has zero open questions — proven, no label issues, always fills. Its tradeoff: a plain stop order can fill well past its nominal target on a fast move (11–25 pips seen on live USDJPY/AUDJPY fills), since it fills at market once triggered, whatever the current price is at that instant.

StopLimit (the default on both VEPFPT and VEPSPT) caps how much slippage is acceptable — trading that protection for a chance of no fill at all on the fastest moves. The Label-mismatch history above applies specifically to this mode.

💡
If switching to StopOrder

Keep position size modest while watching the first several real fills specifically for which of the three outcomes above shows up — that tells you whether StopLimit is behaving safely in practice if you go back to it, not just in theory.

Order Placement

Why does Max Stop-Limit Slippage need to scale per symbol?

A flat pips number treats every symbol as if it moves similarly, which isn't true — confirmed for real when a live CADJPY order got cancelled by the broker itself (no cancel request from the cBot at all), since a fixed 5 pips was a far tighter real cap there than intended. Max Stop-Limit Slippage (x ATR) scales this correctly per-symbol, same as every other distance parameter, controlled by the same Distance Unit Mode switch, on both cBots.

Signal Detection

Why does the empty bin count look wrong on my chart?

This was a real, confirmed bug carried from the original tools: the counting logic counted any zero-volume bin anywhere in the scan window — not just a genuinely unbroken run from the true price extreme. A pattern like [empty, filled, empty] wrongly counted as 2 empty bins, when only the first one is actually connected to the edge.

⭐
Fixed everywhere, all at once

The count now walks inward from the true price extreme and stops counting the instant it hits real volume — matching exactly what "empty bins at the boundary" should mean. This is the same logic behind the indicator's chart labels and both VEPFPT's and VEPSPT's own boundary lines and EDGE EXH detection.

Signal Detection

Why are Min Empty Bins split into High/Low instead of one shared value?

A real structural bias, not a symmetry choice: volume is attributed by each candle's CLOSE price only, not its full high/low range. Whichever candle set the profile's High almost never closed exactly there — so the very topmost bin shows empty far more often than genuine exhaustion alone would explain. The bottom side has a milder version of the same bias.

💡
Why compensate instead of fixing the root cause

A true fix would mean rewriting how volume gets attributed to bins across the whole profile — affecting POC/VAH/VAL too, a much larger and riskier change. A stricter Min Empty Bins (High/Sell Side) threshold (default 2 on both cBots) compensates for the bias directly, without touching the core profile math.

Signal Detection

What's the difference between the EMPTY label and the boundary line (VEPFPT/VEPSPT)?

Same underlying data, two different visual purposes. The EMPTY text labels mark every bin that's part of the genuine consecutive void. The boundary line (both cBots) marks specifically the innermost edge of that void — where real trading activity actually resumed. Both are computed from the exact same consecutive-count logic, so they can never disagree with each other.

Manual Trades & Risk

If I place a manual trade with the right Comment tag, does it get BE/trailing automatically?

Yes — if it has an SL already. Manual Trade Integration means any trade where Label or Comment matches the cBot's own Label gets full management: BE, trailing, restart recovery, concurrent-trade counting, daily-loss protection, Discord alerts.

⚠️
The one real gap this didn't originally cover

See the next question — a manual trade with genuinely no SL at all didn't get BE/trailing until a dedicated fix was built for it. This is now handled on both VEPFPT and VEPSPT via Missing-SL Auto-Attachment, but it's worth understanding why it wasn't automatic before.

Manual Trades & Risk

What happens if I place a manual trade with no SL at all?

Originally: nothing good. BE/trailing depend on a risk-distance value only ever set when the cBot's own order-arming logic places a trade — a manual trade never goes through that path, so the stop-management check's very first guard meant BE was never even evaluated for it, not just "delayed."

⭐
Now fixed with direction-aware auto-attachment

Both cBots scan continuously (every 15s) for a recognized position with no SL, and attach one from Max SL Distance and current ATR. If price is already favorable, the new SL anchors off current price (locks in the move). If already unfavorable, it anchors off entry price instead — so Max SL Distance keeps meaning "a real, honored cap on total risk from entry" everywhere, not something that can silently balloon.

This is a backstop, not a substitute for deliberate SL placement — it uses a generic ATR-scaled distance, not a real structural stop anchored to that specific trade's own setup.

Manual Trades & Risk

Does a trade need to match on Label, Comment, or both?

Either one is enough. The actual check is label == OrderLabel || comment == OrderLabel — an exact, case-sensitive match on just one of the two fields is sufficient for a trade to be recognized as the cBot's own.

Manual Trades & Risk

Will VEPFPT recognize a trade tagged "VEPSPT", or vice versa?

No. Each running instance only ever recognizes its own configured Label — VEPFPT's check is hardcoded to whatever its own Label parameter says (default VEPFPT), and has no awareness of VEPSPT at all, or vice versa. Making them recognize each other's trades was considered and deliberately rejected — it would mean both cBots trying to independently manage the same position (conflicting BE/trailing modifications, a daily-loss breach on one force-closing the other's trades too), a worse problem than the one it would solve. This is exactly why the Symbol-Wide Open-Position Gate exists instead — it blocks a new order from either bot when any open position already sits on that symbol, rather than letting two bots fight over managing the same one.

Manual Trades & Risk

Why doesn't Max Concurrent Trades count my manual or untagged trades?

The same Label/Comment matching described above applies here too — a trade with no matching Label or Comment at all is completely invisible to this count, exactly as it is to every other trade-recognition check.

⚠️
A real, concrete risk worth knowing

If a StopLimit order ever slips through with a blank label and becomes a real position (the UNTRACKED POSITION OPENED case), that position is also invisible to Max Concurrent Trades — the cBot could then open a second, fully-tracked trade believing it's still at zero, while the orphaned one sits unmanaged in the background. Treat that alert as meaning your real exposure just increased, even though the dashboard won't reflect it.

General

What's the core difference between VEPFPT and VEPSPT?

Profile anchoring, and nothing else architecturally. VEPFPT runs a rolling, fixed-bar lookback window — no session concept, so its historical signal display can drift from the live window over time (a structural trade-off, not a bug). VEPSPT instead hard-resets its profile at a calendar-anchored session boundary (Daily/Weekly/Monthly), so each session gets its own frozen profile with no drift — but it also doesn't get VEPFPT's three extra EDGE EXH Alone gates, and it has two slightly lower expiry caps (MA Cross Confirmation Expiry and Expiry Bars). See the Comparison Table tab for the full breakdown.

General

Why does only VEPFPT have the extra EDGE EXH Alone gates?

Those three gates — Volume Confirmation, PDC Distance Filter, Extreme Stall Gate — were built specifically to compensate for the rolling window's own weaknesses: a rolling profile can keep sliding under a signal, so an extra volume check, a distance floor, and a stall check all help filter out weaker EDGE EXH Alone entries before committing capital. A session-anchored profile's frozen boundary doesn't have that same failure mode, so VEPSPT's EDGE EXH Alone path was kept to the plain toggle. If you want those extra filters on a session-anchored entry, that's currently an VEPFPT-only capability — not yet ported to VEPSPT.

General

What does Distance Unit Mode actually control?

A single global switch (under General on both cBots) deciding whether SL Buffer, Max SL Distance, Break-Even Trigger, Trailing Distance, Entry Buffer, and Max Stop-Limit Slippage all calculate from an ATR multiple, or from flat pip values — every one of those parameters has both an (x ATR) and a (pips) version, and this switch decides which set is actually in effect. Whichever mode is off is completely ignored, no matter what value sits in it.

General

My trailing stop seems stuck — is that a bug in the cBot?

Once trailing hands off under Native mode, it's 100% cTrader's own native platform feature — confirmed directly in the log ("native trailing stop enabled... No further manual SL calls"). Neither cBot touches the SL again after that point, so anything trailing does or doesn't do afterward is a cTrader platform question, not something in this codebase to fix. Manual mode (the default on both) stays under this cBot's own control the entire time instead, specifically to avoid this class of question.

💡
If you want to report it

Pull the exact Journal timestamps around the moment it should have moved, plus a chart screenshot — that combination is concrete enough to be a useful report to cTrader/broker support directly.

General

Why do chart lines/labels look delayed compared to the indicator?

The indicator redraws continuously, every tick — standard behavior for a cTrader indicator evaluating the live bar. Both cBots redraw from OnTick as well, throttled by Chart Redraw Interval (sec) — default 8 — rather than on every tick, which keeps the UI responsive when running several symbol/cBot instances at once.

⭐
Tunable now, not hardcoded

This interval used to be a hardcoded 2 seconds. It's now a real parameter on both VEPFPT and VEPSPT — raise it for less visual lag across many instances, lower it toward 2 for the snappiest possible redraw on a single chart. PDC History Periods (default 2, was hardcoded to 5) works the same way for how many past PDC lines get drawn — fewer lines, less redraw cost.

General

Should I use the cBots, indicators, or the Pine (TradingView) ports?

They're not interchangeable choices — each covers a different need. The cBots (VEPFPT, VEPSPT) are the only ones that place real orders; use them when you want cTrader itself managing entries, SL, BE, and trailing automatically. The cTrader indicators (VEPF, VEPS) are visual-plus-alert only — use them if you want to trade manually off the signals, or if you're running a cBot and want the fuller visual/dashboard picture alongside it (indicators carry a few things the cBots don't need, like POC/VA TRAP/REJECTION detection on VEPF and the AI bias call). The Pine ports (VEPF · TV, VEPS · TV) are for TradingView specifically — same EDGE EXH detection and alert-tier logic as their cTrader indicator counterparts, free, no account beyond TradingView itself, but indicator-only like the cTrader pair: no order placement, and the AI provider integration and License System are deliberately excluded since Pine has no account/network layer to gate them with.

🎯
Rolling vs session still applies on every platform

The Flow/Session split (fixed-bar rolling window vs. calendar-anchored hard reset) is the same architectural choice everywhere it shows up — VEPF vs VEPS on cTrader's indicator, VEPFPT vs VEPSPT on cTrader's cBot, and VEPF · TV vs VEPS · TV on Pine. Pick rolling or session once, based on how you want the profile to behave, then pick whichever of the three platforms matches what you're actually trying to do with it.

Not kept in lockstep release-for-release

The Pine ports mirror the cTrader indicators' core detection and alert logic, but aren't guaranteed to carry every single cTrader-side addition the same day it ships — check each Pine tab's own Recent Updates section for what it's actually caught up to, rather than assuming version parity with the cTrader side.
